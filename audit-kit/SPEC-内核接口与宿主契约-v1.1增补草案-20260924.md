## §A′ 治理面在中库形态的落点（补 §A 的第三种实现）

§A 的九个符号在中库**不换语义、只换载体**：

| §A 符号 | 中库落点 | 与 v1 的差异 |
|---|---|---|
| `open` / `append` / `verify` / `count` / `head` | 库内 `gov/` 载荷（audit-kit 原样装配进库目录） | 无（同一份代码，见 §F′ 载荷哈希对账） |
| 触发器 `no_update` / `no_delete` | `kb.db` 建库即装；`verify` 实测报 `2/2 在位` | 无 |
| `meta['schema_version']` | 双载体（`schema_version` 表 / `meta` 表）任一在位即认，清单里申报 | v1 只写单键；中库落地时**双认**，此处如实登记 |
| `anchor` / `scan` | `tools/kb.py anchor` / `scan`（G5 语义同） | 无 |
| 能力令牌四关 | 中库=**本地常设能力**（L1 单写者）：`CAP` 在 `tools/kb.py` 内声明 `expires=None`；**无签发/撤销运行时面** | 待裁问题①：这一条算 §A 该行的"第三种豁免声明"，还是算中库不适用 §A 该行 |

中库**额外**提供两样 v1 未命名的东西，本增补给它们名分：

1. **库目录结构本身即审计物**——`kb.db` / `kb.manifest.json` / `gov/` / `evo/` /
   `kinds.yml` / `prereg/` / `tools/kb.py` 七件缺一即不合格（§K 结构七查）；
2. **清单（manifest）**——载荷版本申报 + 逐件哈希 + 聚合哈希 + 库锚，见 §F′。

## §C′ 宿主面向什么编程（中库侧）

§C 的四个抽象在中库不变。要补的是一句边界：`tools/kb.py` 是**宿主自己的胶水**，
命令面（12 条：`add import query verify promote tombstone anchor scan decide override
audit sources`）**不随治理件版本走**，也不构成对外契约；对外契约仍是 §C 的抽象与
（共库侧）协议面八工具。改 `kb.py` 的命令名不等于改 SPEC，但**必须同步治理矩阵判据**
（`build/tests/test_governance_matrix.py` 的野命令检查会红）。

## §E′ 一致性测试的完整入口（补 §E 缺的第三条）

```
py -X utf8 audit-kit/conformance.py --kernel audit-kit --host memsys   # 重装形态（13 项）
py -X utf8 audit-kit/conformance.py --fused evo-seat/evo_seat.py       # 融合形态（14 项）
py -X utf8 audit-kit/conformance.py --kb <库目录>                      # 中库形态（31 项）  ← 本增补补的一行
```

- `--kernel` 的参数在中库/装配产物语境下允许给**任一产物目录**（镜像树/平铺二布局），
  原字面量 `audit-kit` 仍有效；
- 项数是**读数不是判据**：判据是"全过才 exit 0"，项数随检查面增长而变（v1 期 12→现 13、
  中库 30→31 皆为例），故本件不把任何项数写进符合性定义；
- **三态不得压平**：`PASS` / `N/A`（未检查）/ `FAIL` 三态分列计数。中库的"库文件锚点比对"
  在库被写入后固定显示 `N/A`（锚点只对建库/迁移那一刻负责）——**"没查"绝不计入"通过"**。
  这一条是 §D 第 4 款 fail-closed 在读侧的延伸，不是新规则。

## §F′ 副本对账在中库形态的落点（补 §F）

§F 讲的是"合并形态自带 `framework_sha`"。中库的对账义务同性质、不同载体：

| 对象 | 对账方式 | 失败语义 |
|---|---|---|
| `gov/` `evo/` 载荷 | 逐件 sha + 聚合 `aggregate_sha` + 载荷内嵌清单 sha **三处互指** | 任一不符 = FAIL（改了载荷没改清单，或反之） |
| `kb.db` | 与清单登记的"库锚"比 | 在锚点处比；库被写后转 `N/A`（历史态），不判红 |
| 升格/降格搬运 | 源库与目标库 `events`/`head`/`digest` **三同** | 三同任一不成立即拒（不是"警告后继续"） |

**新增一句合宪性要求**：`framework_sha` 只覆盖融合件机制段（§1 core…§6 gates），
不含 §7 CLI——故 CLI 面改动**不会**被它抓到，这类改动由治理矩阵判据与行为对拍负责。
（v1 未写明这一覆盖面边界，容易被误读成"有 framework_sha 就什么都对账了"。）

## §G′ 注入面在中库形态（补 §G）

§G 的"两个入口、一道门"与 JSONL 交换格式在中库同样成立：`add`（单条）/
`import`（批量，逐行构造校验 + `content_hash` 幂等去重 + 坏行计数拒）。
**批量≠放宽**这句从微内核条款升格为跨形态通则（三形态实测同形，见留痕对拍）。

## §H′ 三形态的定位（把架构口径写进规范）

| 形态 | 等式 | 载体 | 治理面 |
|---|---|---|---|
| 微内核 | L1 × 融合单文件 | 一个 `evo_seat.py` | 档位静态权限（§A 豁免声明） |
| 中库 | L1 × 包内自足 | 一个 `kb/` 目录 | 本地常设能力，无签发面 |
| 共库 | L2 × 服务件 | 一个进程 + MCP 协议 | 令牌签发/撤销在 ops 面 |

三者**同一内核语义**（§D 五条一字不改），差别只在"装在哪里、给谁用、能力从哪来"。
